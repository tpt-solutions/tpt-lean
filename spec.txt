tpt-lean Design Specification
Version: 0.2-draft
Project: tpt-lean
Primary language: Rust
Purpose: Fast, embeddable, AI-friendly tooling around Lean 4
Project license: MIT
Dependency policy: No Apache-2.0-only dependencies
Core rule: Lean remains the trusted proof checker. tpt-lean accelerates the workflow around Lean.
1. Summary
tpt-lean is a Rust-native tooling suite for Lean 4.
It does not try to replace Lean’s kernel, Mathlib, or theorem-proving foundations. Instead, it makes Lean easier and faster to use by improving:
project setup
build orchestration
caching
search
editor tooling
profiling
formatting
documentation generation
AI/agent access through MCP
cross-language access through FFI and APIs
The central idea:
Lean checks the mathematics. tpt-lean makes the surrounding experience fast, scriptable, embeddable, and pleasant.
2. Goals
2.1 Primary goals
Make Lean easier to start using
simpler project initialization
dependency setup helpers
health checks
better error explanations
searchable Mathlib index
Make Lean faster in daily use
parallel orchestration
aggressive caching
persistent local daemon
fast symbol search
incremental indexing
profiling tools
Make Lean usable by AI agents
MCP server
structured JSON output
goal/state inspection
context bundling
machine-readable diagnostics
safe tool execution boundaries
Make Lean embeddable in other platforms
C ABI FFI crate
local HTTP/JSON-RPC API
optional WASM build for browser/Node use
generated client SDKs
Stay legally and operationally simple
MIT project license
no Apache-2.0-only dependencies
minimal dependency tree
modular crates
solo-maintainer-friendly scope
3. Non-goals
tpt-lean should not initially attempt to:
rewrite the Lean kernel
replace Lean’s type checker
reimplement Mathlib
create a new theorem prover
fully parse and understand .olean internals on day one
bypass Lean verification
become a cloud service by default
become a fork of Lean
Lean remains the authoritative source of truth for elaboration, type checking, and proof validity.
4. Licensing and dependency policy
4.1 Project license
tpt-lean itself should be licensed under: MIT or Apache 2.0

Forbidden by default:
Apache-2.0-only
GPL-only
AGPL-only
LGPL-only
proprietary
unknown/custom unclear licenses

Important distinction:
A crate licensed as MIT OR Apache-2.0 can be acceptable because it can be used under MIT.
A crate licensed only as Apache-2.0 is rejected.

7.2 tpt-lean-adapter
This is the compatibility layer with official Lean tooling.
Why this matters
Lean’s internal formats and elaboration APIs can change. tpt-lean should avoid relying on unstable internals too early.
The adapter should support multiple capability levels:

Level 1: CLI integration
  Invoke lean/lake and parse output.

Level 2: LSP integration
  Query official Lean language server for goals, diagnostics, symbols.

Level 3: Lean sidecar
  A small Lean program emits structured JSON using Lean APIs.

Level 4: Native artifact reader
  Optional future .olean/.ilean reader, only if stable enough.

Initial implementation
Start with:
lean --version
lake --version
lake env printenv
controlled lake build
controlled lean invocation
Lean LSP JSON-RPC client
optional Lean sidecar for structured symbols/goals
Important rule
The adapter should never silently run arbitrary shell commands from AI/API input.
Commands must be constructed from safe, typed options.
7.3 tpt-lean-syntax
A fast, lossless syntax layer for Lean files.
Purpose
This is not a full Lean elaborator.
It should support:
tokenization
concrete syntax tree parsing
comment preservation
indentation tracking
declaration boundary detection
tactic block detection
import extraction
lightweight symbol extraction
formatting
source spans
Useful for
formatter
lightweight search
import analysis
syntax-aware context packing
editor navigation before full elaboration is available
Design
Use a lossless CST model similar in spirit to modern compiler tooling:

pub struct SyntaxNode {
    pub kind: SyntaxKind,
    pub range: TextRange,
    pub children: Vec<SyntaxElement>,
}

pub enum SyntaxElement {
    Node(SyntaxNode),
    Token(Token),
}

Full semantic information should come from Lean, not this crate.

7.7 tpt-lean-fmt
Fast Lean formatter.
Important design choice
Formatting should be syntax-preserving and conservative.
Lean has significant indentation and tactic syntax, so the formatter should avoid aggressive rewrites early on.
MVP formatting
normalize trailing whitespace
normalize final newline
normalize indentation
align simple tactic blocks
format imports
standardize spacing around common tokens
preserve comments exactly
Commands
tpt-lean fmt
tpt-lean fmt --check
tpt-lean fmt src/Main.lean
tpt-lean fmt --diff

Safety
The formatter should refuse to write output if the syntax tree is invalid or uncertain.
Optional verification mode:
tpt-lean fmt --verify

This runs Lean after formatting to ensure the file still checks.

9. FFI crate: tpt-lean-ffi
Yes, there should absolutely be an FFI crate.
The FFI crate makes tpt-lean usable from:
C
C++
Go
Python
TypeScript/Node native addons
C#
Swift
Kotlin/Native
any platform that can call a C ABI
9.1 Design rules
The FFI boundary should expose:
opaque handles
plain C structs
explicit lengths
explicit ownership
stable error codes
no Rust panic unwinding
no Rust types crossing the boundary

Do not expose:
String
Vec
Result
Box
Arc
HashMap
Tokio runtime types
Rust lifetimes

9.4 Header generation
Use a C header as the public ABI contract.
Options:
hand-written header initially
generated header later if useful

Do not make header generation a blocker for the first release.
9.5 Thread safety
Document each handle type:
TptlContext       thread-safe
TptlIndex         thread-safe for reads
TptlBuildSession  not thread-safe unless documented
TptlSearchResults immutable after creation
9.6 FFI versioning
Separate ABI version from crate version.
uint32_t tptl_abi_version(void);

Breaking ABI changes require a major ABI bump.
10. API server: tpt-lean-server
The API server makes tpt-lean available to tools that do not want to use FFI.
10.1 Default transport
Local-first:
Unix domain socket on Linux/macOS
named pipe or localhost TCP on Windows

Optional:
localhost HTTP

Remote access should be disabled by default.
10.2 API style
Use JSON-RPC 2.0 for the core API.
Endpoint:
POST /v1/rpc

Example:
{
  "jsonrpc": "2.0",
  "id": "1",
  "method": "search.query",
  "params": {
    "query": "continuous compact maximum",
    "limit": 10
  }
}

Response:
{
  "jsonrpc": "2.0",
  "id": "1",
  "result": {
    "items": [
      {
        "name": "IsCompact.exists_isMaxOn",
        "kind": "theorem",
        "score": 0.94,
        "summary": "A continuous function on a compact set attains its maximum."
      }
    ]
  }
}

12. Security model
Because AI agents and APIs can trigger tools, security boundaries matter.
12.1 Default stance
local-only
workspace-only
read-heavy
explicit write permissions
explicit build permissions
no arbitrary shell execution

12.2 Permission classes
Read:
  search
  inspect symbols
  read diagnostics
  context pack

Write:
  format file
  apply import suggestion
  edit files

Build:
  run Lean/Lake
  create artifacts
  update cache

Profile:
  run controlled Lean checks with timing

Network:
  optional dependency fetch
  optional remote cache

12.3 Path safety
Every API/MCP request involving paths must be checked against allowed workspace roots.
Reject:
../../etc/passwd
absolute paths outside workspace
symlink escapes
unexpected device files

12.4 Command safety
Do not accept this:
{
  "command": "rm -rf /"
}

Accept typed requests instead:
{
  "project": ".",
  "target": "Main",
  "timeout_seconds": 120
}

The server constructs safe commands internally.
12.5 Resource limits
Every Lean process should have:
timeout
memory limit where supported
cancellation token
output size limit
environment sanitization
13. Performance targets
These are initial targets, not guarantees.
Warm search
p50: < 10 ms
p95: < 50 ms

Context pack
p50: < 100 ms
p95: < 500 ms
excluding fresh Lean elaboration.
Formatting
5,000-line file: < 100 ms

for syntax-only formatting.
Cache-hit build overhead
< 200 ms overhead before Lean work

Index refresh
incremental file update: < 1 s for syntax index
semantic refresh depends on Lean

16. Optional WASM support: tpt-lean-wasm
WASM is useful, but should not be in the critical path initially.
Good WASM candidates
syntax tokenizer
formatter
local text utilities
search over a prebuilt compact index
AST/CST viewer
documentation search
Bad WASM candidates initially
spawning Lean
running Lake
full build orchestration
native filesystem indexing
native process profiling
WASM should expose a restricted browser-safe subset.

21. Final proposed identity
tpt-lean should be positioned as:
A fast Rust-powered toolbox, API, MCP server, and FFI layer for Lean 4.
Not:
A replacement theorem prover.
The strongest version of the project is a practical acceleration layer that people install because it makes Lean feel easier immediately.
